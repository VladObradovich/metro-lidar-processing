# Metro Perception

Обнаружение посторонних объектов перед поездом метро по облакам 3D-лидара. Система работает на ROS 2 Humble, публикует состояние пути и расстояние до ближайшего подтверждённого препятствия. Для запуска достаточно Docker и записи rosbag2: устанавливать ROS на хост не требуется.

Подробное описание алгоритма, параметров, интерфейсов и экспериментов — в [полном техническом руководстве](https://drive.google.com/file/d/1BU3VcRPWfM5Mh0jl_KJJZlTUixUHr5Yv/view?usp=sharing).

Работа системы показана в [демонстрационном видео](https://drive.google.com/file/d/1_9_It3_lSCxCkDqKueKew3rsrSPAQhi3/view?usp=sharing).

## О проекте

**Вход:** `sensor_msgs/msg/PointCloud2` из лидара или bag-файла. **Выход:** `metro_perception_interfaces/msg/PathAssessment` с одним из трёх состояний:

| Состояние | Значение |
|---|---|
| `OBSTACLE` | Есть подтверждённый объект внутри габарита и конечная положительная дальность до него. |
| `NO_OBSTACLE_DETECTED` | Кандидатов нет в пригодной проверенной области. При предполагаемой калибровке область должна простираться минимум на 50 м. |
| `UNKNOWN` | Данных или доверия к геометрии недостаточно для одного из двух решений выше. |

Штатный профиль использует габарит 2,1 м по ширине и 3,0 м по высоте. Он настроен для известного переднего сектора лидара с **предполагаемой**, а не измеренной калибровкой. Результат не является командой управления тормозами: принимающая система должна отдельно определить реакцию на каждое состояние, включая `UNKNOWN`.

## Как работает алгоритм

1. Облако проверяется, очищается от некорректных точек и приводится к системе координат, где направление движения соответствует положительной оси X.
2. По точкам тоннеля оцениваются опора пути и его ось; вокруг оси строится габарит поезда и определяется фактически проверенная дальность.
3. Кандидаты ищутся двумя каналами: `MOTION` выделяет изменения относительно истории облаков, `GAUGE` ищет объекты внутри габарита без требования движения.
4. Геометрические фильтры отделяют кандидатов от конструкций тоннеля. У края габарита сохраняется неопределённость положения оси пути.
5. Временной монитор связывает кандидатов между кадрами, подтверждает треки и формирует итоговое состояние с расстоянием. Если вход устарел или геометрия непригодна, он сохраняет `UNKNOWN`.

Это геометрический подход на C++17 без обучения сети. Для него не требуются GPU, одометрия поезда или IMU. Краткая схема потока:

```text
rosbag2 / PointCloud2
        |
        v
perception_node -> FrameAnalysis -> obstacle_monitor_node -> PathAssessment
        |                                           |
        +-> облако с метками                       +-> маркеры и RViz (по запросу)
```

## Быстрый старт

Нужны Git и Docker Engine; для варианта с RViz также нужны Linux с локальной графической сессией, плагин Docker Compose и `python3`. ROS 2 на компьютере устанавливать не нужно. Для первой сборки Docker-образа потребуется интернет; если образ уже загружен через `docker load`, можно работать без сети. Команды выполняются в терминале компьютера, если не указано, что вы уже вошли в контейнер.

Склонируйте репозиторий и перейдите в него:

```bash
git clone https://github.com/VladObradovich/metro-lidar-processing.git
cd metro-lidar-processing
```

Поместите папку с записью rosbag2 в `rosbags/`. Внутри этой папки должны находиться `metadata.yaml` и файл данных (`.db3` или `.mcap`). Сами записи не входят в репозиторий. В командах ниже замените `ИМЯ_ПАПКИ` на название папки с записью.

### С графикой: RViz

**1. Запустить контейнер.** При первом запуске Docker соберёт образ; это может занять несколько минут.

```bash
bash scripts/desktop.sh up
```

**2. Терминал 1 — запустить детектор и RViz.** Выполните первую команду из корня репозитория на компьютере. После неё откроется оболочка контейнера; вторую команду введите уже в ней. Оставьте терминал открытым.

```bash
bash scripts/desktop.sh shell
ros2 launch metro_perception_bringup perception.launch.py rviz:=true
```

**3. Терминал 2 — проиграть запись.** Откройте ещё один терминал на компьютере, перейдите в папку репозитория и войдите в тот же контейнер. `ros2 bag info` покажет состав записи; затем запустите воспроизведение.

```bash
bash scripts/desktop.sh shell
ros2 bag info /data/ИМЯ_ПАПКИ
ros2 bag play /data/ИМЯ_ПАПКИ
```

**4. Терминал 3 (по желанию) — смотреть результат в тексте.** Откройте его в корне репозитория на компьютере. Сообщение содержит `state`, `reason`, `distance_m` и `distance_valid`; завершить вывод можно через Ctrl+C.

```bash
bash scripts/desktop.sh exec ros2 topic echo /metro/assessment
```

**5. Завершить работу.** Остановите запущенные команды через Ctrl+C в терминалах 1 и 2, выйдите из оболочек контейнера командой `exit`. После этого в терминале компьютера из корня репозитория остановите контейнер:

```bash
bash scripts/desktop.sh down
```

В RViz слева сверху — depth-видео (серый — дальность, зелёный — коридор движения, красный — препятствие), слева снизу — состояние пути и дальность, справа — облако точек с той же раскраской и габаритом коридора. До первого кадра и после остановки проигрывания состояние `UNKNOWN`: это не сбой.

Полезное про `scripts/desktop.sh`:
- `up --build` пересобирает образ после изменений в коде;
- `up --no-nvidia` запускает без видеокарты NVIDIA, RViz рисует через Mesa; без флага NVIDIA подключается сама, если установлен NVIDIA Container Toolkit;
- `METRO_BAGS_DIR=/путь/к/bag bash scripts/desktop.sh up` монтирует в `/data` другой каталог вместо `rosbags/`;
- через `ssh -X` окно RViz не откроется: нужна локальная графическая сессия или удалённый рабочий стол.

### Без графики

На сервере без дисплея используйте runtime-образ без RViz. Из корня репозитория соберите образ и запустите детектор:

```bash
docker build -f docker/Dockerfile.runtime --target runtime -t metro-lidar:local .
docker run --rm --init --name metro-demo --user "$(id -u):$(id -g)" \
  -v "$PWD/rosbags:/data:ro" \
  metro-lidar:local ros2 launch metro_perception_bringup perception.launch.py
```

Во втором терминале проиграйте запись:

```bash
docker exec metro-demo metro-entrypoint ros2 bag play /data/ИМЯ_ПАПКИ
```

В третьем терминале можно смотреть состояние пути:

```bash
docker exec metro-demo metro-entrypoint ros2 topic echo /metro/assessment --field reason
```

## Обработка другого bag-файла

Положите запись в `rosbags/<имя>/` (или укажите её каталог через `METRO_BAGS_DIR`) и проигрывайте её как `ros2 bag play /data/<имя>`. Штатный входной топик — `/lidar_points`. Какие топики есть в записи, показывает `ros2 bag info /data/<имя>`. Если облако записано под другим именем, передайте его при запуске детектора:

```bash
ros2 launch metro_perception_bringup perception.launch.py rviz:=true \
  input_topic:=/sensing/lidar/hesai128/pointcloud
```

Без графики то же самое — последним аргументом в `docker run ... ros2 launch ...`.

Путь после `input_topic:=` здесь лишь пример: возьмите точное имя из `ros2 bag info`. Профиль геометрии выбирайте **по типу и установке сенсора**, а не по имени bag. Для сенсора с неизвестной ориентацией нельзя считать штатное допущение подтверждённой калибровкой; до её проверки сохраняйте `UNKNOWN`.

Если нужен файл с результатом обработки одного bag без проигрывания топика, запустите офлайн-оценщик с новым именем выходного файла:

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD/rosbags:/data:ro" \
  -v "$PWD/results:/results" \
  metro-lidar:local \
  ros2 run metro_perception_ros evaluate_bag \
  /data/doubleT_platform /lidar_points /results/doubleT_platform-run.jsonl
```

Офлайн-оценщик использует тот же C++ алгоритм и временной монитор. Он не перезаписывает существующий выходной файл; для повторного прогона задайте новое имя.

## Конфигурация

Основной запуск задаётся аргументами `perception.launch.py`:

| Аргумент | По умолчанию | Назначение |
|---|---|---|
| `input_topic` | `/lidar_points` | Топик входного облака. |
| `namespace` | `metro` | Префикс выходных топиков. |
| `sensor_profile` | Установленный `forward_sector_assumed.yaml` | Геометрия сенсора, ROI, настройки детектора и временного монитора. |
| `algorithm_config` | Установленный `algorithm.yaml` | ROS-параметры загрузки и ограничения размера облака. |
| `runtime_config` | Установленный `runtime.yaml` | QoS, возраст результата, ожидание TF и watchdog. |
| `rviz` | `false` | Визуализация с RViz в desktop-образе. |
| `use_sim_time` | `false` | Время ROS; при `true` требуется воспроизведение с `/clock`. |

Исходный штатный профиль: [forward_sector_assumed.yaml](metro_perception_ros/config/forward_sector_assumed.yaml). Профиль сенсора — обычный YAML, а `algorithm_config` и `runtime_config` — файлы ROS-параметров; их форматы не взаимозаменяемы. Для своего профиля передайте доступный **внутри контейнера** путь через `sensor_profile:=/results/my-sensor.yaml` и сначала проверьте направление осей, высоту установки и доверие к калибровке.

Ключевые настройки штатного профиля: `corridor_half_width_m=1.05`, `corridor_height_m=3.0`, `assumed_clear_min_range_m=50.0`. Поля и допустимые диапазоны задаёт [config.hpp](metro_perception_core/include/metro_perception_core/config.hpp). Не подбирайте пороги под отдельное имя bag: это скрывает ошибки геометрии и плохо переносится на контрольные записи.

Для визуальной проверки используйте desktop-образ:

```bash
bash scripts/desktop.sh up
bash scripts/desktop.sh exec ros2 launch metro_perception_bringup perception.launch.py rviz:=true
bash scripts/desktop.sh down
```

## Результат и интерфейсы

| Топик стандартного запуска | Тип | Содержание |
|---|---|---|
| `/lidar_points` | `sensor_msgs/msg/PointCloud2` | Вход по умолчанию. |
| `/metro/analysis` | `metro_perception_interfaces/msg/FrameAnalysis` | Кандидаты и диагностика одного кадра. |
| `/metro/assessment` | `metro_perception_interfaces/msg/PathAssessment` | Состояние пути, причина, расстояние и heartbeat. |
| `/metro/markers` | `visualization_msgs/msg/MarkerArray` | Визуализация при включённом `visualizer` или `rviz`. |

Качество на предоставленных записях — ложные тревоги, пропуски и кадры с недостатком данных по каждому bag, а также разбор записи с синтетическими препятствиями — приведено в разделе [Эксперименты и ограничения](#эксперименты-и-ограничения).

`reported_objects` в оценке — кандидаты текущего кадра, **не подтверждённые треки**. Подтверждение видно по `tracks`; при устаревании данных список объектов очищается, а исходный ключ наблюдения сохраняется. Если `distance_valid=false`, значение `distance_m` отсутствует и передаётся как NaN, а не как ноль. Ориентируйтесь также на `calibration_trust`, `evaluated_range_m`, `stale` и `reason`.

## Архитектура

| Пакет | Ответственность |
|---|---|
| `metro_perception_core` | Подготовка облака, геометрический детектор и временной монитор без зависимости от ROS. |
| `metro_perception_interfaces` | Типы сообщений анализа, кандидатов, треков и решения. |
| `metro_perception_ros` | Онлайн-узлы, адаптер PointCloud2, TF и офлайн-оценщик. |
| `metro_perception_bringup` | Launch-файлы, профили запуска и настройки RViz. |
| `metro_perception_tools` | Утилиты просмотра, метрик и отчётов. |
| `metro_perception_rviz` | Панель результата в RViz; собирается при наличии RViz. |

Онлайн-узлы и `evaluate_bag` используют одно вычислительное ядро. Время bag применяется к разметке, `header.stamp` — к TF, монотонное время — к проверке свежести. При задержках входа обработчик оставляет только последний ожидающий кадр.

## Эксперименты и ограничения

Ниже **зафиксированные результаты прогона `f13e569`**, а не измерение текущего рабочего дерева или оценка на независимых данных. Машиночитаемые показатели и происхождение прогонов сохранены в [metrics-evidence.json](docs/data/metrics-evidence.json).

Каждый кадр получает одно из трёх решений. «Мало данных» — это `UNKNOWN`: пол не найден или виден ближе 50 м, идёт прогрев истории, найденный объект ещё не подтверждён.

**Кадры без препятствия в габарите.** Верный ответ — «свободно», любая тревога ложная.

| Запись | Набор | Кадров | Свободно (верно) | Ложная тревога | Мало данных |
|---|---|---:|---:|---:|---:|
| `doubleT_platform` | разработка | 345 | 298 | 0 | 47 |
| `roundT_pressureGate_roundT` | разработка | 268 | 218 | 0 | 50 |
| `roundT_doubleT` | проверка | 252 | 185 | 0 | 67 |
| `roundT_squareT_pressureGate_squareT` | проверка | 545 | 479 | 0 | 66 |
| `squareT_platform_squareT_switch` | проверка | 877 | 816 | 0 | 61 |
| `new_data`, первые 595 с | разработка | 5 950 | 4 485 | 26 | 1 439 |
| `cloud_with_fake_obj`, кадры без объекта в габарите | регрессия | 833 | 708 | 0 | 125 |
| **Итого** | | **9 070** | **7 189** | **26** | **1 855** |
| `new_data`, остальные 605 с | слепая часть | 5 321 | 4 035 | 16 | 1 270 |

Слепую часть `new_data` при разработке не разбирали по кадрам, для неё известен только итог.

**Кадры с препятствием в габарите.** «Свободно» верно, если объект дальше проверенной области: система утверждает, что путь свободен только до `evaluated_range_m`.

| Запись | Кадров | Тревога | Свободно, объект дальше области | Свободно, объект в области (пропуск) | Мало данных | Объектов найдено |
|---|---:|---:|---:|---:|---:|---:|
| `doubleT_obstacle`, два человека | 201 | 68 | 0 | 59 | 74 | 2 из 2 |
| `cloud_with_fake_obj`, синтетические объекты | 465 | 152 | 209 | 68 | 36 | 6 из 7 |

В `doubleT_obstacle` пропуски такие: 38 кадров, где дальний человек стоит примерно на 55 м и тревога по нему то держится, то снимается, и 21 кадр, где человек ближе 20 м. Запись снята другим лидаром с другой установкой, поэтому пороги по ней не подбирались. В `cloud_with_fake_obj` не найден короб 2×2 м у края габарита. На трёх объектах вне габарита и над ним тревог нет (0 из 250 кадров). Ещё 212 кадров этой записи не оцениваются: вставленный объект даёт там меньше 10 отражений.

**Синтетические препятствия (`cloud_with_fake_obj`) по отдельности.** Объекты стоят друг за другом примерно через 100 м. «Оценивается с» — самая дальняя дистанция, на которой объект есть в разметке; дальше он даёт меньше 10 отражений. «Первая тревога» — дальность, на которой система впервые выдала `OBSTACLE` по этому объекту.

| 3 | Куб 0,3 м | на рельсе | 42,7 | да | 42,7 | 16 из 24 |
| 4 | Куб 0,3 м | в габарите, у края | 44,2 | да | 33,1 | 6 из 24 |
| 5 | Куб 0,3 м | вне габарита, рядом | — | тревог нет (верно) | — | 0 из 101 |
| 6 | Короб 2×2 м | в габарите, у края | 198,4 | **нет** | — | 0 из 102 |
| 7 | Короб 2×2 м | вне габарита | — | тревог нет (верно) | — | 0 из 101 |

Итог: 6 из 7 объектов в габарите найдены, на трёх объектах вне и над габаритом ни одной тревоги. Короб у края (№ 6) пропущен: в 65 из 102 кадров он дальше проверенной области, а в остальных 37 детектор не выделяет его как кандидата. Пределы применения: калибровка штатного профиля предполагается, дальность проверки ограничена наблюдаемой геометрией тоннеля, объекты у края габарита и на развилках остаются сложными. Независимого положительного контрольного набора нет, поэтому приведённые числа не доказывают полноту обнаружения на новом сенсоре. Более подробный разбор и время обработки приведены в [техническом руководстве](docs/ru/index.md).

## Разработка и документация

Для изменений кода используйте Dev Container или [универсальный Docker-образ](docker/Dockerfile): на хосте ROS не нужен. В ROS-окружении команды такие:

```bash
bash scripts/build.sh
source install/local_setup.bash
bash scripts/test.sh
python3 scripts/smoke_monitor.py
python3 scripts/smoke_detector.py
```

Документация хранится в `docs/ru/`. Локальный сайт и PDF собираются из одних источников; для них нужны Python, Doxygen и системные библиотеки WeasyPrint:

```bash
make docs-venv
make docs-host        # сайт на http://127.0.0.1:8000
make docs-build-host  # HTML и PDF в results/docs/ru/
```

В PDF входят руководство и справочники; сайт также содержит C++ API. Версия документа берётся из `metro_perception_core/package.xml`, дата — из дня сборки. Для воспроизводимого выпуска задайте `DOCS_DATE=ГГГГ-ММ-ДД` при вызове `make docs-build-host`.
